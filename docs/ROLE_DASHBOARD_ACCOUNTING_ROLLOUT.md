# تِجرا — لوحات حسب الوظيفة وربط المحاسبة بالبيع (مرحلة تطوير 24 أكتوبر 2026)

**الحالة:** شيفرة في الفرع \`feat/purchase-guardian-20261023\` ضمن DRAFT PR #40. لم يُنفّذ Prisma migration على قاعدة إنتاج أو staging، ولم ينجح CI بعد (Github Actions محظور بحالة billing). ليست ميزة منشورة.

## 1) مصدر البيانات المشترك
- كل مستخدم ينتمي إلى Business فعالة واحدة في جلسته؛ يمكنه التبديل فقط بين عضوياته المخولة.
- المخزون وPOS والمبيعات والعميل والمشتريات والذمم والمحاسبة تقرأ سجلات الشركة نفسها. لا تنسخ قواعد البيانات للموظفين.
- Owner: \`/\` لوحة الأنشطة الكاملة، ثم \`/management/governance\` لتخصيص لوحات الدور، وصلاحيات الموظفين، وفروعهم.
- Manager: \`/workbench\`، Accountant: \`/workbench/accounting\`, Cashier: \`/sales\`; الموظف المتعدد يبدأ \`/workbench\`.
- \`RoleDashboardProfile(businessId, role, widgetKeys)\` يحدد مؤشرات العرض فقط. \`lib/role-dashboard-policy.ts\` يعترض كل مفتاح خارج صلاحية الدور، وعند قراءة الإعداد يتقاطع أيضًا مع الصلاحيات الحالية لكل STAFF. لا يمنح الحساب صلاحية الوصول إلى API بمجرد اختيار مؤشر.
- صلاحيات STAFF للوظائف من \`/api/governance/access\`، ومنح المواقع من \`/api/governance/locations\`; كلاهما حوكمي بخادم وسجل أثر. تقييد الفروع لا يطبق إلا إذا فُعّل \`locationAccessEnforced\` من حوكمة المنشأة.
- \`hasBusinessWideRead\` يمنع عرض تقارير مالية أو إدارية تجميعية لمن مُنح أقل من جميع المواقع النشطة؛ إذا لم يكن سجل الأعمال قابلًا للتصفية حسب فرع حتى الآن، نمنع التقرير بدل تسريب بيانات جميع الفروع. مركز التشغيل يعرض للموظف المهام الممكنة حسب الفرع فقط.

## 2) ربط البيع بالمحاسبة — الوضع الجديد الحقيقي
- عند نجاح \`recordSale\` داخل المعاملة التي تخصم المخزون وتثبت الفاتورة، يُنشأ \`AccountingSourceEvent\` من نوع SALE بنفس المعاملة. إذا فشلت عملية البيع كلها فلا يبقى حدث محاسبي وهمي.
- لكل (businessId, SALE, saleId) مؤشر محاسبي واحد \`@@unique\`. لا يمكن إنشاء مسودتي قيد من نفس الفاتورة عند التزامن بفضل \`Serializable\` والربط الفريد.
- بعد نجاح البيع، تحاول \`draftSaleJournal\` إنشاء مسودة قيد مزدوج دون تعطيل الكاشير إذا تعذرت العملية. إشارة المصدر موجودة لإعادة المحاولة؛ وقد تحتاج إعادة التشغيل عند إصلاح الفترات أو الحسابات.
- إذا اعتمد المالك خريطة حسابات مالية نشطة في \`/accounting/automation\`، يوزع POS النقد والبطاقات والتحويلات والأخرى على حسابات أصول، ويثبت إيراد البيع الإجمالي وتكلفة البضاعة والمخزون بدقة هللات.
- \`FinancialAccount.kind\` يُفحَص على الخادم حسب خانة الربط؛ لا يمكن استخدام حساب تابع لشركة أخرى أو نوع حساب غير ملائم.
- فاتورة سعرها صفر وتكلفتها صفر تُعلّم كمصدر BLOCKED لا قيد صفري.
- **عند وجود رقم ضريبي للمنشأة يُمنع تفعيل التوليد الآلي**؛ النموذج الحالي لا يحتوي تفصيل VAT/إصدار XML صالح للامتثال. حتى في المنشآت بلا رقم ضريبي، لا يُسمح التفعيل إلا بعد إقرار المالك مراجعة أساس الضريبة؛ لا تثبت هذه الموافقة أن المنشأة معفاة رسميًا.
- تُنشأ القيود \`JournalEntry.status = DRAFT\`، ويطبق مسار الترحيل الحالي \`/api/ledger/journals/[id]/post\` أذونات OWNER/ACCOUNTANT وسلامة الفترة، والفصل بين المنشئ والمُرحّل متى فُعِّل \`journalDualApprovalEnabled\`. لا توجد دفعات أو تسويات بنكية تلقائية أو إصدار فواتير ضريبية.
- \`/accounting/automation\` يعرض المصدر وحالة مسودته ومحاولة آمنة لإعادة تجهيز القيد. العمليات القديمة قبل إنشاء المصدر لا تُرحل بأثر رجعي دون مراجعة مستقلة.

## 3) أدوار وحواجز الوصول
- إخفاء الروابط ليس تصريحًا أمنيًا: الصفحات وAPIs تتحقق من العضوية والأدوار والمواقع. أضيفت حواجز نطاق الشركة الواسع في CRM/Flow/Sourcing/Compliance والأقسام المالية الحساسة.
- **لم يتم الانتهاء من تدقيق كل مسارات Next.js القديمة**؛ ما زال مطلوبًا مراجعة API شامل، ومحاكاة هجمات IDOR، واختبارات موظفين بعدة فروع، ومراجعة الوصول إلى ملفات الأشخاص والأجور والفواتير.
- GROUP/FISCAL consolidation وRLS في PostgreSQL وfine-grained grants لكل كيان ما زالت مهام لاحقة، لا يدّعي هذا التغيير تنفيذها.

## 4) معايير القبول على staging قبل النشر
1. تدقيق Prisma schema وأسماء العلاقات وإعداد migrations مراجعة يدويًا، مع نسخة احتياطية واسترداد تجريبي للقاعدة.
2. تشغيل \`npm ci\`, \`npx prisma validate\`, \`npm run db:generate\`, \`npm run typecheck\`, \`npm run build\`, \`npm run audit:governance\` واختبارات \`node --test tests/*.test.mjs\`.
3. التحقق من ظهور المؤشرات المسموح بها فقط لكل دور، وأن تعديل لوحة الدور لا يمنح وصولًا إلى API.
4. اختبار إلغاء فرع من موظف، ثم محاولة الوصول إلى بيانات الفروع الأخرى عبر URL وAPI. اختبار تقييد التقارير التي لا تملك بعد locationId.
5. اختبار فاتورة واحدة مع/بدون مواد خام، و2 طلب متزامنين لنفس الفاتورة، وإعادة محاولة المصدر بعد فشل الفترة، ومنع تكرار قيد المصدر.
6. اختبار عدم ترحيل القيد آليًا عند البيع؛ منشئ قيد وشخص آخر يعتمد حيث تفرض السياسة؛ ومنع الإقفال عند اختلاف الفترة.
7. رفض تشغيل الربط للمنشآت المسجلة ضريبيًا ولحسابات مالية غير صحيحة، وعدم تسمية إيصالات التحصيل اليدوية تسوية بنكية.
8. استكمال ترحيل المشتريات والرواتب والذمم إلى محرك محاسبي مدقق، ومعالجة الضريبة السعودية وتدقيق الامتثال قبل تقديم المنصة كنظام محاسبة مؤسسي كامل.
