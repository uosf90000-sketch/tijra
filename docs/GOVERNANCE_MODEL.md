# تيجرا — مصفوفة الحوكمة الفنية (Governance Baseline)

## تعريف الحوكمة
الحوكمة في تِجرا ليست إخفاء أزرار: كل طلب تعديل حساس يجب أن يُفحص داخل API بعد تحديد المستخدم والشركة النشطة، ويُخزن السبب والفاعل والقرار. واجهات التقارير لا تمثل شهادة تدقيق مستقلة.

## تعريف الفصل في الصلاحيات
- مالك المنشأة: السياسات، صلاحيات STAFF، المراجعة، العمليات الاستثنائية.
- مدير: مراجعة طلبات الشراء التي أنشأها مستخدم آخر، وحركة المخزون مرتفعة القيمة عند منحه الصلاحية المناسبة.
- محاسب: إعداد مسير رواتب وتسجيل المصروفات ضمن حد المنشأة، واعتماد مسير أعده شخص آخر حين تسمح سياسة الرواتب؛ لا يُعد الدفع فعليًا بمجرد تأشير الزر.
- موظف: فقط الصلاحيات الأربع الممنوحة؛ لا ترقية ذاتية.
- المورد الخارجي: رابط موقع ومحدود الزمن لتنفيذ رد الطلب، ولا يسمح بإرسال/اعتماد طلب محجوز للحوكمة.

## السلوك بالنسبة لأحجام المنشآت
- MICRO / SMALL: واجهة بسيطة وخيارات اعتماد يمكن تفعيلها باختيار المالك. سقف خصم الكاشير الافتراضي مرن، ويجب على المالك مراجعته قبل إدخال الموظفين.
- ENTERPRISE الجديدة: الافتراض الابتدائي هو تفعيل فصل طلبات الشراء والرواتب، وإلزام سبب الحركة السريعة، ومنع خصومات الكاشير غير المصرح بها.
- تحويل شركة موجودة إلى ENTERPRISE عبر الواجهة لا يُنشئ تلقائيًا بقية سياسات الامتثال؛ راجع /management/governance واحفظ سياسة مناسبة.
- الإعدادات قابلة للتعديل بمالك الشركة، مع تسجيل التغيير. هذا **ليس اعتمادًا بنظام تفويض سياسات من مجلس الإدارة**.

## ثغرات ومتطلبات باقية قبل ادعاء "محوكم بالكامل"
1. **SSO + MFA + SCIM** وسياسات كلمات المرور وقفل الحساب والتعافي الآمن.
2. **ACL على مستوى الفرع والمستودع/القسم** في كل API، وسياسات row-level/tenant isolation مستقلة مع اختبارات اختراق.
3. موافقات متعددة المستويات لكل المشتريات والعقود والتسويات ومصروفات الأعمال والجرد الكبير بدل الرفض/المالك فقط.
4. محاسبة القيد المزدوج والإقفال ومنع تعديل الفترات المغلقة، والمصادقة البنكية على تسوية الدفعات، ومجموعات حسابات الشركات والتعاملات البينية.
5. سجل تدقيق **خارج قاعدة التشغيل مقاوم للعبث** مع retention/legal hold وعزل الإداريين، لا تعتمد على InventoryAuditEvent كإثبات غير قابل للتغيير.
6. تفويض واستعادة الأجهزة وخيارات الجلسات الموثوقة وكشف إساءة الدخول بمحدّدات معدل موزعة (distributed rate limits).
7. اختبارات الأحمال العالية، عزل الشركة، التزامن أثناء الجرد/الكاشير، مراقبة SLA وDR والنسخ الاحتياطي وخطة الاسترجاع.
8. الامتثال السعودي المناسب للنشاط: ZATCA فاتورة الإلكترونية، وحماية البيانات PDPL والقطاع المحدد؛ يلزم تحليل قانوني وتكامل مع الجهات ذات الصلة.
9. ربط كل إجراء بالمستند الداعم، واعتماد مراجعات الحسابات والموردين والتكاليف.
10. منع خصومات السوق/العقود والتسعير الاستثنائي عبر جميع المسارات الأخرى، وليس الكاشير فقط.

## حواجز النشر
- لا تستخدم db push على قاعدة إنتاج بلا خطة migration واختبار نسخة staging ونسخة احتياطية متحققة.
- GitHub Actions لدى هذا الفرع يعرض "failure" مع steps=null وبدون سجلات قابلة للقراءة؛ لا يوجد تأكيد ناجح لـ typecheck/build أو اختبار اتصال قاعدة البيانات.
- شغّل على staging: Prisma validate/generate, TypeScript, Next build, unit tests, route audit, migrations, end-to-end tests بصلاحيات متعددة وفواتير متكررة، ثم مراقبة بعد نشر تدريجي.
- التأكد من عدم وجود اعتماد ذاتي للرواتب والمشتريات، وعدم عبور بيانات مؤسسة إلى أخرى، وعدم إقرار مصروفات/خصومات خارج الحدود، وعدم إصدار طلب مورد قبل موافقة المراجع.

**الحالة: قاعدة حوكمة متقدمة قيد التطوير، وليست منظومة امتثال مؤسسية مكتملة أو منشورة للإنتاج.**
