# تيجرا — مصفوفة الحوكمة الفنية (Governance Baseline)

## تعريف الحوكمة
الحوكمة في تِجرا ليست إخفاء أزرار: كل طلب تعديل حساس يجب أن يُفحص داخل API بعد تحديد المستخدم والشركة النشطة، ويُخزن السبب والفاعل والقرار. واجهات التقارير لا تمثل شهادة تدقيق مستقلة.

## تعريف الفصل في الصلاحيات
- مالك المنشأة: السياسات، صلاحيات STAFF، المراجعة، العمليات الاستثنائية.
- مدير: مراجعة طلبات الشراء التي أنشأها مستخدم آخر، وحركة المخزون مرتفعة القيمة عند منحه الصلاحية المناسبة.
- محاسب: إعداد مسير رواتب وتسجيل المصروفات ضمن حد المنشأة، واعتماد مسير أعده شخص آخر حين تسمح سياسة الرواتب؛ لا يُعد الدفع فعليًا بمجرد تأشير الزر.
- موظف: فقط الصلاحيات الأربع الممنوحة؛ لا ترقية ذاتية.
- المورد الخارجي: رابط موقع ومحدود الزمن لتنفيذ رد الطلب، ولا يسمح بإرسال/اعتماد طلب محجوز للحوكمة.

## السلوك بالنسبة لأحجام المنشآت
- MICRO / SMALL: واجهة بسيطة وخيارات اعتماد يمكن تفعيلها باختيار المالك. سقف خصم الكاشير الافتراضي مرن، ويجب على المالك مراجعته قبل إدخال الموظفين.
- ENTERPRISE الجديدة: الافتراض الابتدائي هو تفعيل فصل طلبات الشراء والرواتب، وإلزام سبب الحركة السريعة، ومنع خصومات الكاشير غير المصرح بها.
- تحويل شركة موجودة إلى ENTERPRISE عبر الواجهة لا يُنشئ تلقائيًا بقية سياسات الامتثال؛ راجع /management/governance واحفظ سياسة مناسبة.
- الإعدادات قابلة للتعديل بمالك الشركة، مع تسجيل التغيير. هذا **ليس اعتمادًا بنظام تفويض سياسات من مجلس الإدارة**.

## ثغرات ومتطلبات باقية قبل ادعاء "محوكم بالكامل"
1. **SSO + SCIM + فرض MFA المؤسسي والاسترداد**: أضيف TOTP اختياري مشفر، لكن فرضه على الموظفين ورموز استرداد الطوارئ لم ينفذا بعد.
2. **ACL في بقية المسارات**: أضيفت منح الفروع على مستوى العضوية إلى واجهات مخزون وبيع مهمة، لكن إدارة الأقسام وتغطية كل API والعزل عبر RLS واختبارات الاختراق لم تكتمل.
3. موافقات متعددة المستويات لكل المشتريات والعقود والتسويات ومصروفات الأعمال والجرد الكبير بدل الرفض/المالك فقط.
4. **تكامل محاسبة القيد المزدوج**: أضيف دفتر يدوي بفترات مقفلة وقيد متوازن وترحيل، لكن الربط التلقائي بالفواتير والبنوك وتسوية الشركات والتعاملات البينية لم يُنفذ.
5. سجل تدقيق **خارج قاعدة التشغيل مقاوم للعبث** مع retention/legal hold وعزل الإداريين، لا تعتمد على InventoryAuditEvent كإثبات غير قابل للتغيير.
6. تفويض واستعادة الأجهزة وخيارات الجلسات الموثوقة وكشف إساءة الدخول بمحدّدات معدل موزعة (distributed rate limits).
7. اختبارات الأحمال العالية، عزل الشركة، التزامن أثناء الجرد/الكاشير، مراقبة SLA وDR والنسخ الاحتياطي وخطة الاسترجاع.
8. الامتثال السعودي المناسب للنشاط: ZATCA فاتورة الإلكترونية، وحماية البيانات PDPL والقطاع المحدد؛ يلزم تحليل قانوني وتكامل مع الجهات ذات الصلة.
9. ربط كل إجراء بالمستند الداعم، واعتماد مراجعات الحسابات والموردين والتكاليف.
10. منع خصومات السوق/العقود والتسعير الاستثنائي عبر جميع المسارات الأخرى، وليس الكاشير فقط.

## حواجز النشر
- لا تستخدم db push على قاعدة إنتاج بلا خطة migration واختبار نسخة staging ونسخة احتياطية متحققة.
- GitHub Actions لدى هذا الفرع يعرض "failure" مع steps=null وبدون سجلات قابلة للقراءة؛ لا يوجد تأكيد ناجح لـ typecheck/build أو اختبار اتصال قاعدة البيانات.
- شغّل على staging: Prisma validate/generate, TypeScript, Next build, unit tests, route audit, migrations, end-to-end tests بصلاحيات متعددة وفواتير متكررة، ثم مراقبة بعد نشر تدريجي.
- التأكد من عدم وجود اعتماد ذاتي للرواتب والمشتريات، وعدم عبور بيانات مؤسسة إلى أخرى، وعدم إقرار مصروفات/خصومات خارج الحدود، وعدم إصدار طلب مورد قبل موافقة المراجع.

**الحالة: قاعدة حوكمة متقدمة قيد التطوير، وليست منظومة امتثال مؤسسية مكتملة أو منشورة للإنتاج.**


## إضافات فرع التطوير — 23 أكتوبر 2026
- صلاحيات المواقع: منح فروع ومستودعات لكل عضوية بقرار مالك وتسجيل سبب التغيير وإنهاء جلسات الموظف. التفعيل اختياري وغير مفعل افتراضيًا، وعلى المالك توزيع المواقع أولًا.
- حماية الموقع في البيع والجرد والتحويل والاستلام والمرتجعات والشفتات. عمليات الهدر والإقفال والاستلام المركزي التي لا تحدد موقعًا لا يُسمح بها لغير المالك عند تشغيل التقييد.
- حساب المستخدم: TOTP بستة أرقام مشفر بمفتاح AES-256-GCM في خادم التطبيق، مع قفل محاولات ومنع إعادة استخدام الرمز. لا تتوفر رموز استرداد ولا فرض مؤسسي شامل. إعداد مفتاح MFA_ENCRYPTION_KEY المكون من 32 بايت بصيغة base64url ضرورة للتفعيل؛ لا تضعه بالشيفرة.
- المحاسبة: حسابات مستقلة، فترات مالية، قيود يدوية مدين/دائن بالهللات، ترحيل بعد مراجعة وانغلاق الفترة. لا يتم توليد قيود من المبيعات أو المصروفات تلقائيًا ولا توجد تسوية بنكية.
- الاختبارات الجديدة: اختبارات لقواعد صلاحيات المواقع، توافق رموز TOTP والتشفير، موازنة القيود والحظر بعد الإقفال. لم يثبت نجاح البناء بعد لأن GitHub Actions فشل قبل عرض الخطوات.
- تظل سياسة الأمان التقنية ناقصة إلى أن تتوفر المصادقة الاستردادية وSSO/SCIM، وقواعد صلاحيات كل المسارات، وحفظ تدقيق مستقل مقاوم للعبث، واختبارات أحمال واختراق، وتجهيز ضريبة ZATCA والامتثال حسب نشاط العميل.

## شروط تشغيل MFA والمحاسبة
- اختبر على Staging بمفتاح تشفير سري محفوظ في إدارة الأسرار، ولا تفعّل لمستخدم فعلي دون إجراء استعادة حساب موثوق.
- اضبط الفترات ودليل الحسابات عبر محاسب مختص؛ المبالغ الجديدة لا تدخل في التقارير القديمة تلقائيًا كي لا تحسب مرتين.
- حسابات الشركات الكبيرة تحتاج مراجعًا ثانيًا؛ الحساب المنفرد لا يستطيع اعتماد قيوده إذا كان فصل الواجبات إلزاميًا.
- لا تدمج تغييرات قاعدة البيانات أو تنشرها على Railway قبل نسخة احتياطية مجربة، ومراجعة مخطط Prisma، ونجاح الاختبارات والتحقق من الهجرة.

## استكمال أكتوبر 2026: استرداد MFA وتدقيق الصندوق والتصدير
- لكل حساب فعّل Authenticator يتم إنشاء 10 رموز استرداد مستقلة (128-bit) تُعرض مرة واحدة عند التفعيل؛ تُحفظ بصمة SHA-256 لكل رمز فقط، ويستهلك الرمز مرة واحدة بعملية ذرية حتى إذا تزامنت محاولتا دخول. لا يُرسل نص الرمز بالبريد ولا يُخزن كنص صريح.
- يمكن الدخول برمز استرداد + كلمة المرور، وتعطيل المصادقة بالطريقتين نفسيهما، وتجديد رموز الاسترداد القديمة بعد تحقق جديد. تُسجّل أحداث MFA_RECOVERY_LOGIN وMFA_RECOVERY_ROTATED. لا يوجد دعم SSO أو SCIM ولا إنفاذ تلقائي للمصادقة على كل أعضاء مؤسسة.
- يوجد حد لكلمات المرور الفاشلة عبر AuthLoginThrottle في PostgreSQL: 8 محاولات خلال 15 دقيقة يقود إلى منع مؤقت لمدة 15 دقيقة. يحفظ فقط hash للبريد. هذا ليس Rate Limit شبكيًا شاملًا لكل IP أو Firewall خارجي، وما زالت هناك مخاطر إنكار خدمة تستدعي مراقبة تشغيل.
- تصدير تدقيق المالك عبر GET /api/governance/audit/export?days=30: حتى 2500 حدث موثق بتوقيع HMAC-SHA256 يعتمد على مفتاح AUDIT_EXPORT_SIGNING_KEY منفصل من 32 بايت محفوظ في أسرار الخادم. إذا تخطى التصدير الحد، يحدد manifest حالة truncated صراحة. يمكن التحقق من الملف باستعمال scripts/verify-governance-export.mjs في بيئة موثوقة تمتلك مفتاح التحقق.
- HMAC يضمن سلامة النسخة بعد توقيعها لدى من يحافظ على سر التوقيع، لكنه لا يشكّل توقيعًا عامًا مستقلا ولا يخزن التدقيق خارج قاعدة التشغيل أو يمنع مسؤولًا يمتلك المفتاح من إعادة توقيع محتوى مختلف. ما زال مطلوبًا أرشيف خارجي WORM/immutable وفصل IAM ودليل إجراءات احتفاظ.
- أصبح Sale.locationId معرفًا لكل بيع جديد. إقفال الوردية يجمع المبيعات النقدية لنفس الموقع فقط بدل مجموع الشركة. سجلات المبيعات القديمة بلا معرف موقع لا تُنسب آليًا إلى فرع معين إذا كان للشركة عدة مواقع؛ يُرفض الإقفال ويتطلب تسوية تاريخية صحيحة.
- أضيف فحص العضوية والموقع قبل إظهار فاتورة بيع مكررة، مع pg_advisory_xact_lock لمنع تسجيل نفس رقم الفاتورة مرتين في المعاملات المتوازية. منع الموظف من تسجيل بيع بتاريخ قديم، واشتراط رقم فاتورة لمعاملات الشركات ENTERPRISE الجديدة.
- لا تُصلح هذه التعديلات وحدها كامل قيود ZATCA ولا الاسترداد المركزي للهوية ولا سلوك بيع غير متصل Offline مع مزامنة متزامنة. يلزم تغطية جميع المسارات واختبار متكامل.

## حاجز النشر الإلزامي لهذه الدفعة
1. راجع مخطط Prisma وترحيل قواعد staging والنسخ الاحتياطي قبل اعتماد تعديلات Sale وUser وAuthLoginThrottle وMfaRecoveryCode. لا تستعمل مزامنة مخطط قاعدة الإنتاج مباشرة بلا خطة.
2. اختبر استرداد مستخدم MFA عند فقد الهاتف، منع تكرار رمز الاسترداد، قفل المحاولات، تدوير الرموز، وعزل MFA عن المؤسسات الأخرى المرتبطة بالمستخدم.
3. اختبر حساب صندوق ورديتين لموقعين متزامنين وسجلات legacy غير محددة الموقع، وحالتَي بيع بنفس الفاتورة متزامنتين، وموظف يحاول البيع بتاريخ قديم.
4. اختبر توقيع التدقيق وسلامة hash بعد تغيير الحدث، وقاعدة منع التصدير دون مفتاح الخادم، وإخفاء أسرار التشفير والتوقيع في CI وسجلات الخادم.
5. نفّذ TypeScript/Next build واختبارات Node وPrisma وتوافق الهجرة على staging؛ GitHub Actions الحالي فشل دون سجلات job قابلة للقراءة، لذلك لا يوجد دليل على نجاح البناء.
