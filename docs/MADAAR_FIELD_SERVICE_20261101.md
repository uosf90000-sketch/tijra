# مدار — أوامر الخدمات الميدانية (فرع تطوير تجريبي)

## ما تغير
- نموذج ServiceJob مرتبط بمنشأة واحدة، عميل اختياري، موظف معين اختياري، موقع، موعد، قيمة متوقعة، وحالة.
- التتابع الصريح: OPEN -> SCHEDULED (تعيين فني) -> IN_PROGRESS -> COMPLETED، أو CANCELLED بقرار مدير مع سبب.
- الموظف STAFF يرى أوامر الخدمات المسندة إلى سجل Employee المربوط بحسابه فقط، ولا يستطيع إلغاء الأمر أو إعادة إسناده.
- عند تطبيق تحديد الفروع، أوامر الموظف محصورة في المواقع الممنوحة له؛ التقارير الشاملة للمدير/المحاسب تمنع الوصول إذا كانت منح الفروع ناقصة.
- إنشاء الأمر يسجّل SERVICE_COMPLETION في BusinessCommitment بموعد الخدمة. ينعكس إغلاق أمر الخدمة في الالتزام وتظهر التأخيرات عبر مدار Flow، بلا عمل مالي أو إرسال تلقائي.
- إلغاء/إنجاز أمر خدمة يتطلب سببًا لا يقل عن 8 أحرف، مع InventoryAuditEvent بفاعل العملية.
- حماية التزام الخدمة المرتبط بمصدر: لا يمكن إغلاقه من شاشة الالتزامات بدلًا من أمر الخدمة الأصلي.
- idempotency في إنشاء أوامر الخدمة بواسطة clientRequestId UUID وتوقيع SHA-256 للحقول؛ الطلب المكرر يُعاد دون إنشاء عمل مكرر، وتغيّر بيانات طلب بنفس المعرف يُرفض.
- شاشة /service-jobs للمالك والمدير والمحاسب والفني المعين، مدرجة في قوائم الأدوار وإعداد مساحات العمل.
- اختبارات منطق انتقال الحالات داخل tests/service-workflows.test.mjs.

## حدود صريحة
- توثيق اكتمال الخدمة **داخلي**؛ لا OTP أو تحقق من العميل أو إثبات دفع مصرفي.
- تقتصر الاستعلامات على 200 أمر، ولا توجد جدولة تلقائية/رسائل أو اختيار توقيت للفني/خرائط ومواقع GPS.
- لا يوجد بعد جدولة موارد متقدمة، SLA بعقود، مخزون قطع غيار مباشر لكل أمر، فاتورة ضريبية، أو عقد صيانة.
- القيم الواردة تمثل تعاقدًا/تقديرًا وليس مبلغًا مستلمًا، ولا يُنشئ النظام قيودًا مالية تلقائية.
- تعديل مخطط Prisma يحتاج migration بنسخة احتياطية وإجراء rollback مجرّب. **لم ينفذ migration في الإنتاج**.
- CI الأساسي على GitHub تعثر بسبب billing ولم تثبت اختبارات Next.js/Prisma/E2E؛ ممنوع دمج ونشر بناء على هذه التغييرات وحدها.

## اختبارات قبول قبل الدمج
1. جهّز PostgreSQL staging، راجع Prisma diff والمفاتيح الخارجية وطبّق migration مع backup/restore.
2. ثبّت التبعيات وشغّل prisma validate وgenerate، typecheck، build، واختبارات Node.js 24.
3. جرّب عملاء وموظفين من شركتين؛ محاولة إسناد موظف أو عميل من شركة أخرى يجب أن ترفض.
4. موظف مقيد بفرع لا يرى ولا يحدث أمر خدمة لفرع غير مخوّل؛ مدير غير مخوّل للتقرير الشامل يُرفض.
5. إنشاء أمر مرتين بنفس idempotency key لا يكرر الأمر أو الالتزام؛ نفس المفتاح مع بيانات مختلفة يُرفض.
6. كل تغيير حالة يتبع مخطط الانتقال، ويترك أثرًا مفصلًا؛ لا تحويل عميل إلى PAID أو إصدار فاتورة ضريبية.
7. اكتمال/إلغاء أمر خدمة يحدث الالتزام فقط مرة واحدة، ولا يسمح الإغلاق من مسار التعهدات الموازي.

## المتبقي من نطاق مدار الشامل
التصنيع BOM/MRP، مطبخ الطلبات، التجارة متعددة القنوات، عقود الخدمة والقطع والضمان، بنك/ZATCA، SSO/SCIM، التحويلات الآمنة وWMS المتقدم. هذه ليست ميزات منجزة هنا.
